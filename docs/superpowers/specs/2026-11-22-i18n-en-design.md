# English interface language: design

Date: 2026-11-22. Branch `feat/i18n-en`. Approved by the author on the decision pages on
2026-11-22.

## Why

The author wants to submit FPGA SIM to international hackathons. Judges and participants read
English. Without an English interface, a submission makes no sense. The hackathon search
(2026-11-22) showed that submission materials are in English everywhere; no suitable hackathon is
chosen yet, and no deadline is set.

## Goals

- All interface text is available in English: screens, menus, messages, board hints, part
  descriptions, Verilator diagnostic explanations, notes on board pins and devices.
- The language is chosen with a "Русский / English" switch and the address parameter `?lang=en`
  (the link for judges).
- The Russian interface does not change for current students, including in browsers set to Latvian
  and Ukrainian without English in the language list.

## Non-goals

- Examples (`examples/*`) and lessons (`examples/lessons/*`) keep their Russian comments. The
  author's choice: "interface only".
- The text of server errors (`error.text`, `text` in diagnostics) is not translated. The interface
  shows its own text by code; the Russian server text is visible only where the dictionary has no
  string for the code. This goes to "Open: deferred" in `docs/progress.md`.
- Documents (`docs/`), the README and demo access for judges are separate tasks.
- A third language (Latvian) is not done, but the design must not get in its way.

## Anti-goals (failure, even if it "works")

- Any end-to-end test became green by weakening a check.
- The Russian interface changed for a user who chose nothing and sits in a Russian browser.
- A key is in `ru.json` but not in `en.json` (or the reverse), and no test catches it.
- An interface string appeared in component code instead of the dictionary.

## Constraints

- `CLAUDE.md`: the board file and part description formats change only together with the schema in
  `spec/` and the section of the spec `docs/tz-v1.md`. A new decision goes to `docs/decisions.md`
  with a table of contents entry.
- A change to `boards/` requires deploying both the static files and the server (the board file is
  part of the image).
- Core frames do not go into React state; colors are theme variables only.
- `make check` passes; the visible behavior is checked in the browser (screenshots in both themes
  and both languages).
- Deployment, merge and push happen only on the author's command.

## Approaches

1. **A custom `t()` function and a second dictionary `en.json`; the language is chosen at load,
   a change reloads the page.** Chosen. The strings are already in one dictionary, the numbers in
   them stand after a colon ("Messages: {count}"), and English needs no plural forms. A reload
   removes the question of strings computed once (labels on the board canvas, strings built in
   advance).
2. **The i18next library with live language change.** Rejected: rewriting 577 calls and
   subscribing every canvas label to the language change, with no benefit for the task.
3. **Two builds, `/ru/` and `/en/`.** Rejected: two sets of files for every deployment and two
   links, and the switch is still needed.

Board notes (a question the author resolved): **an `{ru, en}` object, as for parts**, with a change
to the schema, the spec and both deployments. Rejected: the option "translations in `en.json` by
board and pin key": it keeps part of the board description outside the board file.

## Structure

### Language choice: `web/src/i18n/index.ts`

- Languages: `ru`, `en`. Type `Language`.
- At load, the module chooses the language once, in this order:
  1. the address parameter `lang` (`ru` or `en`); a found parameter is saved as the choice;
  2. the saved choice in `localStorage` (the key is the builder's decision, in the style of the
     application's other keys);
  3. the list `navigator.languages` in order: the first language that starts with `ru` or `en`
     gives its language; if there is none, Russian (the author's choice of 2026-11-22: a student
     in Latvia with a `lv` or `uk` browser must not get English without warning).
- Exports: `language` (the current language), `setLanguage(lang)` saves the choice and reloads the
  page, `localized(text)` picks a string from an object `{ru, en, …}`: the current language,
  otherwise `ru`.
- `t()` and `tOr()` take the string from the dictionary of the current language; if the key is
  missing, from `ru.json`; if it is missing there too, the key (as now).
- Substitution `{name}`: a value that is an object with a field `ru` (localized text) is shown
  through `localized`. It is needed for the `device` argument of the server note
  `DEVICE_NOT_MODELED`.
- `document.documentElement.lang` is set by language; `web/index.html` stays `lang="ru"` as the
  initial value.

### Dictionary `web/src/i18n/en.json`

- The same keys as `ru.json`, the same `{…}` substitutions. The type `TextKey` stays derived from
  `ru.json`.
- The agent writes the translation. FPGA terms are the common English ones (bitstream is not
  needed; pin, constraint file, testbench, waveform, breadboard, probe). The style is short, as in
  Russian.
- `app.title` is "FPGA SIM" in both.

### Switch

- On the sign-in screen and in the account menu (`AccountMenu.tsx`): a `Choice` or a pair of
  buttons "Русский / English" (the language name is written in the language itself and does not go
  to the dictionary; this is an exception to the rule "strings only in the dictionary" and must be
  recorded in the decision).
- The choice calls `setLanguage`: it first writes the editor draft immediately (now the write runs
  on a timer after 300 ms, `actions.ts:86`, and there is no `pagehide` handler), then reloads the
  page. Test: type and switch the language at once; the edit stays in place.

### Deviations during planning (the agent's decisions)

- The switch stands next to the theme switch (the projects screen, the top bar of the workspace)
  and on the sign-in form, not in the account menu: sign-in by a link with a key has no such menu.
- The help screenshots (`web/public/help/*.png`) were taken from the Russian interface. For
  English, a second set `*-en.png` is taken, and the help uses the set that matches the language.

### Numbers and dates

Six places with a hard-coded language (`format.ts` — `LOCALE`, `speed.ts`, `accounts.ts`,
`PartDialog.tsx:29`, `diagnostics.ts:6`, `BoardView.tsx:205`) take the language from the `i18n`
module. Number locale: `ru-RU` / `en-US`.

### Parts and diagnostics

- `parts/*/part.json`: add `"en"` to every `{ "ru": … }`. The schema already allows it.
- `spec/diagnostics.json`: add `en` to `text` and `explain` of 68 codes (9 more codes have the
  level `hidden` and no text).
- Reading goes through `localized`.

### Board file: a format change

- Fields with human text that the interface shows become a "text by language" object, like
  `$defs/text` in `spec/part.schema.json` (`ru` is required): `pins.*.note`, `devices[].label`.
- `clocks[].label` and `shared[].users[]` stay strings: the interface and the server do not read
  them (only the check `tools/spec/check.mjs:329`). A format translation with no visible result is
  not needed. An item in "Open: deferred": when these fields are first shown, use the same object.
  (The agent's decision.)
- `parts[].label` of built-in parts (`LED0`, `S1`, `UART (BL702)`) stays a string: these are
  silkscreen names, and they are not translated. The board `name` is a string.
- `format` stays `1`: board files ship only from the repository, users do not write them, and
  there are no old copies in projects. (The builder's decision: check that a project's
  `fpgasim.json` does not copy these fields; if it does, raise it as a question to the author.)
- Server `server/fpgasim_server/resolve.py:440` (`DEVICE_NOT_MODELED`): the source text of the
  diagnostic (field `original`) gets `label["ru"]`, and the argument `device` gets the whole
  object. There is no schema for diagnostic arguments in `spec/protocol/`; the argument is
  described in the spec (`docs/tz-v1.md:1054`, `:1066`), and the fix goes there. The expectation
  `"device": "HDMI"` in `server/tests/test_api.py:160` changes to an object: this is a consequence
  of the format change, not a weakened test; state this explicitly in the commit and in the plan.
- The interface reads the fields through `localized`: the pin hint (`scene.ts:432`), the device
  list (`BoardView.tsx`), the clock, the shared pins; everywhere the field is shown now.
- The spec: the row "Interface language | Russian" (`docs/tz-v1.md:46`); sections 3.1–3.3 (format
  and full board files); 7.6, the `device` argument (`:1054`, `:1066`); 9.1 (strings: "English and
  Latvian are added as second files"); 15.2, the row "Latvian language" is clarified.

### Tests

- The end-to-end tests (549 lines with Russian text) and the unit tests (411) get Russian
  explicitly: `locale: "ru-RU"` in `use` of both Playwright configs (`playwright.config.ts`,
  `playwright.prod.config.ts`); Vitest requires a setup file with language `ru`: in Node 26
  `navigator.language` exists and equals `en-US`. The expectations of existing tests do not change,
  except `server/tests/test_api.py:160` (see "Board file").
- A new unit test: the keys of `en.json` = the keys of `ru.json`; the `{…}` sets in each string pair
  match; every `part.json` and `diagnostics.json` has `en` wherever it has `ru`; every board file
  passes the updated schema and has `en`.
- A new unit test of language choice: address > saved choice > browser; `lv` → `ru`;
  `lv, en, ru` → `en`; `uk, ru, en` → `ru`; `localized` with a missing `en` gives `ru`.
- A new end-to-end test: `?lang=en`: the sign-in screen is in English, `html[lang=en]`; sign-in,
  opening an example, a build: the messages and the board pin hint are in English; the switch
  returns Russian after a reload. The state is read through `window.__fpgasim` (add the field
  `language`).
- Server tests: the note `DEVICE_NOT_MODELED` carries an object in `device`.

### Documents

- `docs/decisions.md`: decision 168 "English interface language" (the reason is hackathons; the
  language choice order; reload on change; the board note format; the server is not translated;
  language names outside the dictionary). A table of contents entry.
- `docs/progress.md`: an entry in "After acceptance", an item in "Open: deferred" about the Russian
  server text and about the examples with lessons.
- `CLAUDE.md`, section "What not to do": strings only through `ru.json` and `en.json`.

### Deployment

After the merge on the author's command: `make deploy-web`, then `make deploy-server` (the board
file is in the image, `resolve.py`), then `make e2e-prod`. Static files first: the new interface
accepts the device label both as a string and as an object; the old one would show the object as
JSON (a decision made during execution).

## Left to the builder

- The `localStorage` key, the look of the switch (`Choice` or two buttons), the place on the
  sign-in screen.
- The translation of 577 strings, 68 diagnostics, 30 part strings, about 80 board strings.
- The deployment order, if the check above shows that the old interface breaks.
